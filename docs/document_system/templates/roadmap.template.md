# `roadmap.md` テンプレート

ロードマップは**時系列の計画の羅列**である。チェック付きの箇条書き 1 本で、
「これから何をするか」と「何を終えたか」だけを示す。

## 書式

```markdown
- [<状態>] **<ID>** <一文の what>。<必要なら補足 1 文>。 → #<課題番号>
```

| 要素 | ルール |
|---|---|
| 状態 | `x` 完了 / `空白` 未着手 / `~` 着手中 |
| ID | 起票・議論・参照の共通キー。**一度振ったら変えない** |
| what | **1〜2 文**。何をするかだけを書く |
| `[dep <ID>]` | **未着手・着手中の項目にのみ書く**（下記） |
| `→ #<課題番号>` | 対応する課題。未起票なら省略する |
| 全体 | **1 行 200 バイト以内・子ブロックを持たない** |

## 構造

```markdown
## 予定（上から着手順）

- [ ] **<ID>** …
- [~] **<ID>** …

## 完了

- [x] **<ID>** …
- [x] **<ID>** …
```

最上位の見出しはこの 2 つだけ。**機能軸のグルーピング（フェーズ・エピック等）を作らない**——
時系列と機能軸は両立せず、両方を維持しようとすると必ずどちらかが嘘になる。
「なぜこれらが 1 群なのか」は設計文書が持つ。

完了が増えたら、その中を**時間軸の小見出し**（`### 2026-08` 等）で区切ってよい。
時間軸は並び順と同じ軸なので、時系列と矛盾しない。

## 子ブロックを持たない

項目行の下に説明の入れ子を作らない。これが最も重要な制約である。

実装の記録（何をどう作ったか・判断の論点と結論・検証の内容・残余）は、
書ける場所があれば必ずそこへ流れ込む。子ブロックを許すと、ロードマップは
数か月で「進捗の一覧」ではなく「実装記録の集積場」になり、
進捗を確認するだけのために全体を読む羽目になる。

**書く行が存在しないこと自体が制約**であり、規約の文章より強い。
実装の記録は ID から辿れる別の文書へ置く。

## `dep` を完了項目に書かない理由

依存は「まだ着手できない理由」を表す。完了した項目の依存は
すべて解決済みなので、情報を持たない。時系列に並んでいれば
過去の依存関係は順序が示す。

## 完了項目を消さない理由

ID は外部（設計文書・コード・課題）から参照される。行を消すと
ID から課題番号への対応が失われる。完了項目は**1 行だけ**残す。

## 書かないもの

| 書かないもの | 本来の置き場 |
|---|---|
| 実装の記録・as-built | ID から辿る別文書 |
| 設計判断とその根拠 | それが支配する設計文書 |
| 撤回・置換の経緯 | 同上（項目行には結果を 1 文で書く） |
| 検証の内容・証跡 | 実装の記録 |
| 節・トピックの列挙 | 設計文書の見出し |

撤回された項目も 1 行に収まる。

```markdown
- [x] **<ID>** <何をしようとしたか>。<いつ・なぜ撤回したか。1 文>。 → #<課題番号>
```

## 例

```markdown
## 予定（上から着手順）

- [ ] **7.2** 依存ライブラリの更新運用を定める。 [dep 7.1]
- [~] **6.4** 検索インデックスを再構築する。移行スクリプトの検証待ち。 → #128

## 完了

- [x] **6.3** 検索 API にページングを入れる。 → #121
- [x] **5.9** バッチの再実行機構。#118 で撤回（冪等性を前提にできないため）。 → #104
```

## 機械的な検査

次の 4 点は機械的に検査できる。プロジェクトのテストレーンに載せることを推奨する。

1. 各項目行が上限バイト数以内であること。
2. 項目行の直後に入れ子のリストが無いこと。
3. `[dep …]` が `- [x]` の行に現れないこと。
4. ID が重複していないこと。
