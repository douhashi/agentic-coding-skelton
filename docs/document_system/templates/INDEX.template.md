# `INDEX.md` テンプレート

各ディレクトリの `INDEX.md` は、**そのディレクトリに実在するファイル**だけを列挙する。
INDEX は経路案内であって、内容の要約でも設計の記録でもない。

## 書式

```markdown
- `<file>`: <何のファイルか・何の SSoT か。1 文>
  - 読むとき: <どの作業に着手するとき開くか>
```

- 1 行目は必須。2 行目は任意。
- 2 行目のラベルは `読むとき:` に固定する。
- **1 行 1 文**。これが一次ルール。
- 1 エントリは最大 2 行。
- 機械検査用の backstop として 1 行 200 バイトを上限とする（プロジェクトで調整してよい）。

## 書かないもの

| 書かないもの | 本来の置き場 |
|---|---|
| 節・トピックの列挙 | 本体ファイルの見出し |
| 設計判断・実装の経緯・as-built | 判断を記録する文書 |
| 課題番号・PR 番号 | 進捗を管理する文書 |
| 実装ファイル名・実装層の説明 | コード（下記） |

これらを書く行が存在しないこと自体が制約になる。スロットを増やすと、増やした分だけ埋まる。

## 実装ファイル名を書かない理由

リンクは向きによって壊れやすさが違う。

| 向き | ファイルを移動・改名したとき |
|---|---|
| コード → 文書 | コメントがファイルと一緒に動く。**壊れない** |
| 文書 → コード | 文書が黙って嘘になる。**必ず壊れる** |

「どこに実装があるか」は検索すれば数秒で分かる二次情報であり、
**最も安く再取得できて、最も壊れやすい**。よって INDEX には書かない。

「その実装がどの設計文書に従うか」は**コード側の冒頭コメント**に書く。
これは壊れない向きであり、そのコードを開いた人が必ず目にする。

## 例

```markdown
- `deployment.md`: 本番環境へのデプロイ手順の SSoT。
  - 読むとき: デプロイ・ロールバック・障害時の切り分けを行うとき。
- `api-design.md`: 公開 API の設計方針と互換性ポリシー。
  - 読むとき: エンドポイントを追加・変更するとき。
- `glossary.md`: プロジェクト内で用いる用語の定義。
```

3 件目のように、1 行で意図が伝わるなら 2 行目は書かない。

## 機械的な検査

次の 3 点は機械的に検査できる。プロジェクトのテストレーンに載せることを推奨する。

1. 各行が上限バイト数以内であること。
2. `` - ` `` で始まる行の直後は、`  - 読むとき:` か、次のエントリか、ファイル末尾のいずれかであること。
3. それ以外の行は見出しのみであること。

規約を文章で定めるだけでは守られない。各変更で「もう一言だけ足す」判断は毎回ローカルには正しく、
上限が無ければ全体としては複利で膨らむ。
